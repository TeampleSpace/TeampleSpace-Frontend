# 공통 계약

프론트엔드와 백엔드가 함께 쓰는 요청, 응답, 문서 형식의 기준이다.
프론트엔드는 이 폴더를 복사해 쓰고 형식이나 오류 코드를 따로 만들지 않는다.

이 문서의 기준은 설계서와 지금의 구현으로 백엔드가 정리한 것이다.
프론트엔드가 반영해 확인한 내용은 프론트엔드 저장소의 계약 기록에 남긴다.
실제 API는 각 기능을 개발하는 단계에서 구현하며 어디까지 구현했는지는 아래 구현 상태에 적는다.

## 구성

| 경로 | 내용 |
| --- | --- |
| `schemas/document.schema.json` | 발표 문서, 슬라이드, 요소, 출처 연결 형식. schemaVersion 1 |
| `schemas/api.schema.json` | 오류, 요소 수정 요청과 응답, 이벤트, 작업, 기능 지원 정보, 세션 초기 정보, 동기화 스냅샷 |
| `error-codes.json` | 오류 코드와 HTTP 상태, 근거 |
| `examples/` | 형식별 예제 |
| `examples/invalid/` | 스키마가 거절해야 하는 예제 |
| `examples/manifest.json` | 예제와 스키마의 짝, 통과 여부 기대값 |
| `examples/assets/` | 예제 문서가 참조하는 이미지. 파일 이름이 fileObjectId다 |
| `CHANGELOG.md` | 계약이 바뀐 내용과 프론트엔드가 다시 복사할 때 볼 것 |

`examples/presentation.json`이 편집기 실험과 파일 출력 실험이 함께 쓰는 문서 예제다.
한글, 긴 문장, 줄바꿈, 도형, 이미지, 회전, 출처 연결이 들어 있다.

## 프론트에서 쓰는 방법

`contracts` 폴더를 그대로 복사해 사용한다. 복사한 커밋을 기록해 두고 계약이 바뀌면 `CHANGELOG.md`를 보고 다시 복사한다.

검증은 ajv 8의 2020 판으로 확인했다.

```ts
import Ajv2020 from "ajv/dist/2020";
import documentSchema from "./contracts/schemas/document.schema.json";
import apiSchema from "./contracts/schemas/api.schema.json";

const ajv = new Ajv2020({ schemas: [documentSchema, apiSchema] });

const validatePresentation = ajv.getSchema("document.schema.json");
const validateError = ajv.getSchema("api.schema.json#/$defs/ErrorResponse");
```

`manifest.json`의 각 항목을 돌며 `schema`로 검증한 결과가 `valid`와 같은지 확인하면 백엔드 테스트와 같은 검사가 된다.
예제 파일은 화면 테스트 데이터로 그대로 쓸 수 있다.

## 공통 규칙

- 공개 경로는 `/v1`로 시작한다
- 식별자는 소문자 UUID 문자열, 시간은 UTC ISO 8601, 좌표는 캔버스 단위다
- 버전은 1부터 시작하는 정수이고 JavaScript 안전 정수 범위 안에 있다
- 이벤트 식별자와 이벤트 커서는 문자열로 주고받는다. 클라이언트는 같은지 비교하고 그대로 돌려줄 뿐 크기를 비교하거나 계산하지 않는다

### 버전 범위

서로 다른 범위의 버전은 비교하지 않는다.

| 이름 | 범위 | 증가 조건 |
| --- | --- | --- |
| `userVersion` | 프로필, 계정 연결 상태 | 프로필, 로그인 수단 변경 |
| `projectVersion` | 이름, 주제, 소유권, 삭제 상태 | 해당 정보 변경 |
| `membershipVersion` | 한 사용자와 프로젝트의 관계 | 참여, 퇴장, 소유권 변경 |
| `materialVersion` | 자료 정보와 처리 상태 | 제목, 설명, 현재 원문, 분석 상태 변경 |
| `outlineVersion` | 발표 구성 전체 | 항목, 순서, 근거 변경 |
| `designVersion` | 디자인 설정 | 디자인 저장 |
| `generation` | 전체 생성 세대 | 전체 생성 결과 게시 |
| `presentationVersion` | 문서 내용 전체 | 요소, 슬라이드, 순서 변경. 한 번 바뀔 때 1씩 오른다. 승인, 댓글, 묶음 닫기는 올리지 않는다 |
| `orderVersion` | 슬라이드 목록과 순서 | 추가, 삭제, 순서 변경 |
| `slideVersion` | 슬라이드 내용 | 그 안의 요소 변경 포함 |
| `elementVersion` | 요소 하나 | 요소 수정, 삭제 |

### 헤더

| 헤더 | 방향 | 용도 |
| --- | --- | --- |
| `Idempotency-Key` | 요청 | 문서를 바꾸는 모든 요청에 필수. 재시도할 때 같은 값을 다시 보낸다 |
| `X-CSRF-Token` | 요청 | GET이 아닌 모든 요청에 세션 초기 정보의 `csrfToken`을 싣는다 |
| `Last-Event-ID` | 요청 | 이벤트 구독을 다시 연결할 때 마지막으로 받은 `eventId`를 보낸다 |
| `X-Request-Id` | 응답 | 모든 응답에 서버가 만든 요청 식별자가 온다. 오류 본문의 `requestId`와 같은 값이다. 클라이언트가 보낸 값은 쓰지 않는다 |
| `Retry-After` | 응답 | 429, 다시 시도할 수 있는 503, `REQUEST_IN_PROGRESS` 응답에 초 단위로 온다. 그 전에는 같은 요청을 다시 보내지 않는다 |

## 문서 형식

편집기, 최초 생성 결과, 파일 출력이 같은 형식을 쓴다.

- 발표 문서는 `slideIds`로 순서를, `slides`로 내용을 가진다. 슬라이드도 `elementIds`와 `elements`를 가진다
- 요소 종류는 `text`, `shape`, `image`이고 종류에 따라 `content`와 `style`이 정해진다
- 이미지는 `fileObjectId`로만 참조한다. 임의 외부 URL은 넣을 수 없다
- `assetUrl`은 읽기 응답에만 붙는 임시 주소이고 저장하지 않는다
- 출처 연결은 자료, 개정, 개정 번호를 고정한다. 자료가 지워지면 `sourceDeleted`로 표시한다

스키마로 표현하지 못하는 조건은 서버가 따로 검사한다.

- `slideIds`와 `slides`, `elementIds`와 `elements`의 식별자와 순서가 같다
- 슬라이드의 `presentationId`, `generation`이 문서와 같고 요소의 `slideId`가 슬라이드와 같다
- 좌표와 크기는 소수 넷째 자리까지 저장한다

## 요소 수정과 재시도

요청은 `ElementPatchRequest`, 성공 응답은 `MutationResponse`다.
`patch`에 보낸 `geometry`, `content`, `style`은 항목마다 통째로 교체된다. 보내지 않은 항목은 그대로다.

서버는 아래 순서로 처리한다.

1. 인증과 프로젝트 참여 여부를 확인한다
2. 같은 멱등키의 기존 결과를 버전 검사보다 먼저 찾는다. 같은 키와 같은 본문이면 처음과 같은 상태 코드와 응답을 돌려준다. 충돌 같은 거절 결과도 그대로 돌려준다
3. 같은 키인데 본문이 다르면 `IDEMPOTENCY_KEY_REUSED`, 같은 키를 처리하는 중이면 `REQUEST_IN_PROGRESS`와 `Retry-After`를 돌려준다
4. 새 요청일 때만 `generation`과 `baseVersion`을 검사하고 문서 변경, 변경 이력, 이벤트, 멱등 결과를 한 트랜잭션으로 저장한다

클라이언트 규칙은 다음과 같다.

- 응답을 받지 못했으면 멱등키, `clientMutationId`, 본문 전체를 그대로 다시 보낸다
- 다음 편집부터 새 멱등키와 새 `clientMutationId`를 만든다
- `clientMutationId`는 응답과 이벤트를 자기 요청과 잇는 값이다. 멱등키를 대신하지 않는다
- `VERSION_CONFLICT`는 자동으로 다시 보내 덮어쓰지 않는다. 응답의 `currentVersions`에는 현재 버전만 있으므로 최신 내용은 이미 받은 이벤트나 동기화 스냅샷에서 얻는다
- 멱등 결과 보관 기간이 지나면 다시 보내지 않고 동기화 스냅샷을 읽어 비교한다

### 편집 묶음

저장할 때마다 검토 이력이 생기지 않도록 연속 저장을 `editGroupId`로 묶는다.

- 같은 작성자, 편집 세션, 세대, 요소의 연속 수정이 하나의 변경이 된다. 묶음 식별자는 처음 만든 작성자, 편집 세션, 요소에만 쓸 수 있고 다르게 쓰면 `VALIDATION_FAILED`다
- 묶음이 열릴 때 `change.created`, 닫힐 때 `change.finalized` 이벤트가 한 번씩 나간다. 그 사이의 내용은 `element.updated`로 전달된다
- 열린 묶음은 승인할 수 없다. 닫힌 묶음의 처음 이전 내용과 마지막 이후 내용은 바뀌지 않는다

묶음은 아래 경우에 닫힌다.

| 경우 | 누가 판단하나 | 방법 |
| --- | --- | --- |
| 2초 동안 저장이 없음 | 서버 | 서버가 요청을 받은 시각으로 판단한다. 같은 프로젝트의 다음 쓰기나 변경 조회 때 닫는다 |
| 묶음을 연 지 30초가 지남 | 서버 | 위와 같다 |
| 다른 작성자가 같은 요소를 수정 | 서버 | 그 수정을 저장할 때 닫는다 |
| 같은 편집 세션이 다른 요소를 저장 | 서버 | 그 저장을 처리할 때 이전 요소의 묶음을 닫는다 |
| 입력란을 벗어남, 다른 요소나 슬라이드로 이동, 편집 종료, 발표나 내보내기 전 저장 밀어내기 | 클라이언트 | `finalizeGroup`이 true인 요청을 보낸다 |

- 시간 기준은 서버가 판단하므로 클라이언트는 시간 때문에 닫는 요청을 보내지 않아도 된다. 보내더라도 문제는 없다
- `finalizeGroup`이 true인 요청은 `patch`와 함께 보내 마지막 저장과 닫기를 한 번에 할 수 있다
- `patch` 없이 보내면 묶음만 닫는다. 내용 버전은 오르지 않고 멱등키와 `clientMutationId`는 새로 만든다. 이때는 세대만 확인하고 `baseVersion`은 확인하지 않는다
- 닫힌 묶음의 `editGroupId`로 저장하거나 닫는 요청을 보내면 `EDIT_GROUP_CLOSED`가 온다. 저장이었다면 최신 상태를 확인한 뒤 새 묶음으로 다시 보내고, 닫는 요청이었다면 이미 닫힌 것으로 본다
- 브라우저가 닫는 요청을 보내지 못해도 서버가 시간 기준으로 닫는다

## 오류

모든 오류는 `ErrorResponse` 형식이다. 코드와 상태는 `error-codes.json`에 있다.

- 충돌이면 `currentVersions`, 입력 내용 오류면 `fieldErrors`가 함께 온다
- 잘못된 JSON, 허용하지 않는 메서드, 지원하지 않는 본문 형식처럼 프레임워크가 거절한 요청도 같은 형식이다. HTTP 상태와 `Allow` 같은 헤더는 원래대로 온다
- 응답의 `message`는 코드마다 정해 둔 문구다. 파서 메시지, 예외 이름, 요청 내용은 들어가지 않는다
- 예상하지 못한 오류는 `INTERNAL_ERROR`와 500으로 오고 원인은 같은 요청 식별자로 서버 로그에서 찾는다
- 클라이언트는 상태 코드가 아니라 `code`로 처리 방법을 고른다. 모르는 코드는 상태 코드에 따라 처리한다

주소 자체를 해석할 수 없는 요청은 서블릿 컨테이너가 먼저 거절해 이 형식이 아닌 400이 온다. 요청 식별자도 붙지 않는다.

## 이벤트

- SSE의 `id`는 `eventId`, `event`는 `type`, `data`는 `Event` 형식의 JSON이다
- 구독은 동기화 스냅샷의 `eventCursor` 다음부터 시작한다
- 같은 `eventId`를 다시 받으면 버린다
- 요소 변경 이벤트의 `payload`는 요소 수정 응답과 같은 항목을 쓴다. 응답과 이벤트 중 어느 쪽이 먼저 와도 같은 `clientMutationId`와 버전으로 한 번만 반영한다. 이미 가진 것보다 오래된 요소 버전은 버린다
- 문서 버전을 올리는 이벤트는 `presentationVersion`과 `generation`을 싣는다. 받은 `presentationVersion`이 알고 있는 값보다 2 이상 크면 중간 변경을 놓친 것이므로 동기화 스냅샷을 다시 읽는다
- 변경 묶음 이벤트의 `payload`는 `changeId`와 `groupState`다
- `presence.updated`는 일시적인 접속 표시이며 다시 받을 수 있다고 보장하지 않는다

### 다시 연결할 때

| 상황 | 순서 |
| --- | --- |
| 연결만 끊겼고 보낼 입력이 없음 | `Last-Event-ID`로 다시 구독해 그 뒤의 이벤트를 이어 받는다 |
| 보내지 못한 입력이 있음 | 프로젝트 참여 여부 확인, 동기화 스냅샷 읽기, 내 입력과 비교, 같은 멱등키로 다시 보내기 순서로 한다 |
| `snapshot_required` 신호를 받음 | 동기화 스냅샷을 다시 읽고 그 `eventCursor`부터 구독한다 |

`snapshot_required`는 커서가 보관 범위를 벗어났거나 올바르지 않을 때 온다. 아직 없는 이벤트를 가리키는 커서도 여기에 든다.

## 작업 상태

`queued`, `running`, `succeeded`, `failed`, `canceled` 다섯 가지다.
끝난 상태는 바뀌지 않는다. 내부 재시도는 같은 작업의 `attempt`가 오르고 사용자가 다시 시도하면 새 작업이 만들어진다.

## 형식을 정한 경로와 구현 상태

형식은 0단계에서 정했고 HTTP 경로는 각 기능 단계에서 연다. 지금 열려 있는 `/v1` 경로는 없다.

| 기능 | 경로 | 형식 | 구현 상태 | HTTP 경로를 여는 단계 |
| --- | --- | --- | --- | --- |
| 요소 수정 | `PATCH /v1/slides/{slideId}/elements/{elementId}` | `ElementPatchRequest`, `MutationResponse` | 저장 처리와 시험이 있다 | 4단계 |
| 이벤트 구독 | `GET /v1/projects/{projectId}/events` | `Event`, `SnapshotRequired` | 이벤트 기록과 커서 뒤 재생, 시험이 있다 | 4단계 |
| 동기화 스냅샷 | `GET /v1/projects/{projectId}/sync-snapshot` | `SyncSnapshot` | 문서와 커서를 같은 시점에 읽는 처리와 시험이 있다. 팀원, 디자인, 작업, 자료 요약은 없다 | 4단계 |
| 기능 지원 정보 | `GET /v1/capabilities` | `Capabilities` | 형식만 | 1단계 |
| 세션 초기 정보 | `GET /v1/auth/bootstrap` | `AuthBootstrap` | 형식만 | 1단계 |
| 디자인 설정 조회 | `GET /v1/projects/{projectId}/design-settings` | `DesignSettings` | 형식만 | 3단계 |
| 프로젝트 작업 목록 | `GET /v1/projects/{projectId}/jobs` | `JobList` | 형식만 | 2단계 |
| 작업 조회 | `GET /v1/jobs/{jobId}` | `Job` | 형식만 | 2단계 |
| 팀 메모 조회 | `GET /v1/materials/{materialId}/note` | `MaterialNote` | 형식만 | 2단계 |
| 팀 메모 저장 | `PUT /v1/materials/{materialId}/note` | `MaterialNotePutRequest`, `MaterialNoteSaveResponse` | 형식만 | 2단계 |

단계 번호는 개발 순서의 번호다. 1은 인증과 프로젝트, 2는 자료, 3은 구성과 디자인, 4는 편집과 공유 저장, 5는 최초 생성, 6은 이력과 검토, 7은 발표와 내보내기다.

## 기준으로 정한 기술 선택

설계서에 값이 없던 항목 가운데 설계와 구현으로 판단할 수 있는 것을 기준으로 정리했다.

| 항목 | 기준 | 근거 |
| --- | --- | --- |
| 요청 식별자 헤더 | `X-Request-Id`. 서버가 만들고 클라이언트 값은 쓰지 않는다 | 구현과 시험이 있다. 클라이언트 값을 받으면 로그를 흐릴 수 있다 |
| CSRF 헤더 | `X-CSRF-Token`. GET이 아닌 요청에 싣는다 | 프론트엔드 클라이언트가 이미 이 이름을 쓴다. 스프링 시큐리티의 세션 기반 기본 헤더 이름과 같다. 검증은 인증을 만드는 1단계에서 구현한다 |
| 수정 요청의 교체 방식 | 보낸 항목을 통째로 교체 | 부분 병합 규칙이 필요 없고 요청 본문 비교가 단순하다. 서버 구현과 프론트엔드 모킹이 같은 방식이다 |
| 이벤트 식별자 | 프로젝트 이벤트 순번의 십진 문자열. 클라이언트는 같은지만 비교 | 설계서가 이벤트 순번을 불투명한 문자열로 다루게 했다 |
| 이벤트 누락 판단 | `presentationVersion`이 2 이상 건너뛰면 스냅샷을 다시 읽음 | 문서 변경 한 번이 문서 버전을 1 올린다. 설계서가 문서 버전 공백을 재조회 조건으로 들었다 |
| 다시 연결하는 순서 | 위 표와 같음 | 1차 출시 기준의 구독 규칙과 연결 끊김 규칙을 상황별로 나눴다 |
| 묶음 종료 | 시간 기준은 서버가, 화면에서만 알 수 있는 종료는 클라이언트가 알림 | 1차 출시 기준이 시간을 서버 수신 시각으로 정했고 브라우저 종료 이벤트에 의존하지 않게 했다 |
| 닫는 요청의 버전 확인 | 세대만 확인 | 내용이 바뀌지 않는다. 서버 구현과 프론트엔드 모킹이 같은 방식이다 |
| 묶음 식별자 오용 | `VALIDATION_FAILED` | 묶음은 작성자, 편집 세션, 요소에 묶인다 |
| 변경 묶음 이벤트의 payload | `changeId`, `groupState` | 구현과 예제가 있다 |
| 삭제 응답 | `tombstone`에 `resourceType`, `id`, `version`, `deletedAt` | 설계서의 삭제 표시를 필드로 옮겼다 |
| `snapshot_required` 본문 | `projectId` | 받으면 할 일이 스냅샷 재조회 하나뿐이다 |
| 이미지 자르기 | 원본 대비 0과 1 사이 비율 | 이미지 해상도와 무관하고 PPTX의 자르기 표현으로 그대로 옮겨진다 |
| 읽기 응답의 이미지 주소 | `assetUrl` | 설계서가 읽기 응답에만 임시 주소를 붙이게 했다 |
| 세션 초기 정보 | `status`, `csrfToken`, `expiresAt`, 로그인했을 때만 `user` | 설계서의 항목을 필드로 옮겼다 |
| 동기화 스냅샷의 편집 범위 | `presentation`, `members`, `designSettings`, `activeJobs`, `materials` | 설계서가 든 다섯 가지를 필드로 옮겼다 |
| 기능 지원 정보의 구조 | 스키마의 `Capabilities` | 설계서의 항목을 필드로 옮겼다. 값은 아래 사용자 결정 항목이다 |
| 항목별 오류 | `fieldErrors`에 `field`, `code`, `message` | 입력란과 요약에 연결하는 데 필요한 최소 항목이다 |
| 오류 코드의 상태 | `error-codes.json`의 `basis`가 기술 선택인 항목 | 설계서의 상태 구분인 401, 403, 404, 409, 413, 422, 429, 503에 맞췄다 |
| 캔버스 단위 | `px`. 파일 출력에서 1px을 0.75pt로 바꾼다 | 편집 화면이 px로 그리고 출력 실험이 이 환산으로 PowerPoint 기본 크기와 맞았다 |
| 문서 형식의 범위 | 도형은 `rect`와 `ellipse`, 글자 스타일은 요소 단위 | 편집 실험과 출력 실험이 이 범위로 확인됐다. 넓히려면 `schemaVersion`을 올린다 |

## 사용자 결정이 필요한 항목

제품 정책이거나 외부 제공자에 달린 값이라 확정하지 않았다. 예제의 값은 형식을 보여 주기 위한 것이다.

| 항목 | 지금 상태 |
| --- | --- |
| 슬라이드에서 쓸 수 있는 글꼴과 웹폰트 제공 | 예제는 Pretendard를 쓴다. 기능 지원 정보의 `fonts`는 비워 두었다 |
| PowerPoint에 글꼴이 없을 때의 정책 | 출력 실험에서 글꼴이 바뀌어 줄바꿈이 달라졌다 |
| 한글 줄바꿈 | 편집 화면은 글자 단위, PDF와 PowerPoint는 낱말 단위로 나뉜다. 하나로 정해야 한다 |
| 출처 연결을 파일에 표시하는 방식 | 출력 실험은 일반 글자인 출처 문구만 옮긴다 |
| 내보내기 형식을 지원한다고 공개하는 기준 | 기능 지원 정보의 `formats`는 비워 두었다 |
| 기본 캔버스 크기 | 예제는 1280x720이다. 문서마다 `canvas`를 가지므로 형식에는 영향이 없다 |
| 업로드 허용 형식과 크기 | `uploadTypes`는 비워 두었다 |
| 목록 크기 | 예제의 기본 30과 상한 100은 설계서의 제안값이다 |
| 약관 문서의 종류, 버전, 주소 | `legalDocuments`는 비워 두었다. 비어 있으면 가입 완료를 열지 않는다 |
| 프로젝트에 참여한 적 없는 사용자의 응답 | 지금은 403이다. 대상이 있는지 숨기려면 404로 바꿔야 한다 |
| 메일, 소셜 로그인, AI, 파일 저장소 제공자와 배포 환경 | 정해지지 않았다 |

## 이후 단계에서 정할 항목

| 항목 | 단계 | 미루는 이유 |
| --- | --- | --- |
| 편집 세션을 식별하는 방법, 세션 쿠키, CSRF 검증 | 1단계 | 인증과 세션을 만들 때 정해진다. 지금은 호출자가 식별자를 넘긴다 |
| 입력 내용 오류를 422와 `fieldErrors`로 응답 | 1단계 | 입력 검증을 쓰는 첫 기능에서 적용한다. 지금은 형식 오류만 400으로 응답한다 |
| 동기화 스냅샷의 작업 공간 범위 | 1단계 | 프로젝트와 팀원 기능이 있어야 내용이 정해진다 |
| 작업 종류 이름과 `inputVersions`의 항목 | 2단계 | 작업 처리 기반을 만들 때 정한다. 예제의 이름은 보기용이다 |
| 출처 연결 저장과 수정 | 2단계 | 자료 개정 테이블이 있어야 한다. 지금 응답의 `sourceRefs`는 비어 있다 |
| 동기화 스냅샷의 구성 범위 | 3단계 | 구성과 디자인 기능이 있어야 내용이 정해진다 |
| 요소 삽입, 삭제, 슬라이드 추가와 순서 변경의 요청 본문 | 4단계 | 응답 형식은 `MutationResponse`로 같다. 요청은 편집 기능을 만들 때 정한다 |
| 요소 종류별 내용과 스타일의 서버 검증 | 4단계 | 지금은 객체인지만 확인한다 |
| 글자 범위별 스타일이 필요한지 | 4단계 | 편집 화면을 만들 때 확인한다 |
| 이벤트 구독 HTTP 연결과 보관 기간 정리 | 4단계 | 지금은 기록과 재생 처리만 있다 |
| 컨테이너가 거절하는 요청의 응답 형식 | 배포 구성을 정할 때 | 프록시와 서버 구성에 달려 있다 |

## 계약을 바꿀 때

스키마, 예제, `manifest.json`, `error-codes.json`을 함께 고치고 `./gradlew test`로 확인한다.
바뀐 내용은 `CHANGELOG.md`에 적는다.
문서 형식이 호환되지 않게 바뀌면 `schemaVersion`을 올린다.
