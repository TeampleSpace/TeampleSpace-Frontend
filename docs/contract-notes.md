# 계약 연결 기반 기록

프론트엔드가 서버 계약을 어떻게 쓰는지, 아직 합의되지 않은 항목이 무엇인지, 무엇을 어떤 방법으로 확인했는지 남기는 문서다.

## 기준

- 제품 범위와 공통 규칙은 노션의 1차 출시 기준과 개발 순서를 따른다. 2026-11-18에 읽었다
- 요청, 응답, 문서 형식은 백엔드 저장소의 공통 계약을 그대로 쓴다. 프론트엔드에서 형식이나 오류 코드를 따로 만들지 않는다

## 계약 폴더

`contracts` 폴더는 백엔드 저장소 `contracts` 폴더의 복사본이다. 직접 고치지 않는다.

| 항목 | 값 |
| --- | --- |
| 복사한 저장소 | TeampleSpace/TeampleSpace-Backend |
| 복사한 기준 | `main`의 fde772b. 계약을 마지막으로 바꾼 커밋은 0e5f916 |
| 복사한 날 | 2026-11-18 |

계약이 바뀌면 폴더를 통째로 다시 복사하고 위 표를 고친 뒤 `npm test`를 돌린다. 어긋난 곳은 `src/shared/api/contracts.test.ts`가 알려 준다.

### 복사본이 최신인지 확인하는 방법

테스트는 복사본을 기준으로 돌기 때문에 복사본이 오래되어도 통과한다. 실제로 서버 내부 오류 코드와 요청 식별자 헤더 설명이 빠진 채 테스트가 통과한 적이 있다. 그래서 복사본과 백엔드 계약을 직접 비교하는 검사를 따로 둔다.

```bash
npm run contracts:check
```

- 옆 폴더 `../Backend`의 `main`에 커밋된 `contracts`와 복사본을 비교한다. 백엔드에서 작업 중인 미커밋 변경은 보지 않는다
- 같으면 기준 커밋을 알려 주고 통과한다. 다르면 다른 줄을 보여 주고 실패한다
- 저장소 위치는 `BACKEND_DIR`, 비교할 브랜치나 커밋은 `BACKEND_REF`로 바꿀 수 있다
- CI의 계약 검사가 백엔드 저장소의 기본 브랜치를 받아 같은 비교를 한다. 이 검사가 실패하면 코드 문제가 아니라 복사본을 다시 맞춰야 한다는 뜻이다

2026-11-18에 최신 복사본에서 통과하고, 오류 코드 파일만 이전 것으로 되돌린 복사본에서는 다른 줄을 보여 주는 것을 확인했다.

같은 날 백엔드 저장소의 작업 브랜치에서 오류 코드 목록의 항목 이름을 바꾸고 코드를 더하는 변경이 진행 중인 것을 봤다. 아직 `main`에 없으므로 반영하지 않았다. 머지되면 위 검사가 실패로 알려 주고 그때 다시 복사한다.

## 프론트엔드에서 계약을 쓰는 방식

- 화면 코드가 쓰는 형식은 `src/shared/api/contract.ts`와 `src/entities/presentation/schema.ts`에 있다. 계약 스키마를 옮긴 것이고 응답을 받을 때 이 형식으로 검사한다
- 예제 문서와 편집 화면 스냅샷은 계약의 예제 파일을 그대로 쓴다. 백엔드의 파일 출력 실험과 같은 문서다
- 모킹 서버는 오류의 HTTP 상태와 재시도 여부를 `contracts/error-codes.json`에서 읽는다. 목록에 없는 코드는 쓸 수 없다
- 서버는 모든 응답에 `X-Request-Id` 헤더를 싣는다. 요청 클라이언트는 공통 오류 형식이 아닌 응답을 받아도 이 값을 남겨 서버 로그와 이어 볼 수 있게 한다
- 서버 내부 오류처럼 상태가 500 이상인 응답은 반영 여부를 알 수 없다. 편집 세션은 자동으로 다시 보내지 않고 입력을 남기며, 사용자가 다시 시도하면 같은 멱등 키와 본문으로 보낸다
- 서버가 준비되기 전에는 `src/mocks/server.ts`의 모킹 서버로 확인한다

`src/shared/api/contracts.test.ts`가 세 가지를 확인한다.

- 계약의 예제 목록 전체가 스키마 검사에서 기대한 통과 여부와 일치한다. 백엔드 테스트와 같은 검사다
- 프론트엔드 형식이 계약의 올바른 예제를 모두 받아들인다
- 모킹 서버의 응답과 이벤트, 편집 세션이 보내는 요청이 계약 스키마를 통과한다

## 아직 합의되지 않은 항목

백엔드가 제안으로 채워 둔 항목은 `contracts/README.md`의 합의가 필요한 항목에 있다. 캔버스 단위와 크기, 텍스트 스타일 범위, 도형 종류, 이미지 자르기 표현, 수정 요청의 교체 방식, 이벤트 식별자 형식, 세션 초기 정보와 스냅샷의 항목 이름이 여기에 들어 있다. 프론트엔드는 지금 이 제안을 그대로 따른다. 묶음만 닫는 요청은 세대만 확인한다는 제안도 여기에 있고 모킹 서버가 같은 방식으로 동작한다.

아래는 프론트엔드 작업 중에 나온 항목으로 계약에 아직 없다.

| 항목 | 프론트엔드의 현재 처리 | 위치 |
| --- | --- | --- |
| CSRF 토큰을 싣는 요청 헤더 이름 | 계약의 헤더 표에 없다. `X-CSRF-Token`으로 임시 지정 | `src/shared/api/contract.ts` |
| 공통 오류 형식이 아닌 오류 응답 | 백엔드는 스프링이 직접 거절하는 요청 오류를 아직 공통 형식으로 바꾸지 않는다. 클라이언트는 계약과 다른 응답으로 분류하고 헤더의 요청 식별자만 남김 | `src/shared/api/client.ts` |
| 이벤트를 놓쳤는지 판단하는 기준 | 이벤트 식별자는 해석하지 않으므로 이벤트의 `presentationVersion`이 직전보다 2 이상 크면 놓친 것으로 보고 스냅샷을 다시 읽음. 문서 버전을 올리는 모든 이벤트가 이 값을 싣는지 확인 필요 | `src/features/editor/session.ts` |
| 다시 연결할 때의 순서 | 보낼 입력이 없으면 마지막 이벤트 뒤부터 재생만 받고, 보낼 입력이 있으면 스냅샷을 먼저 읽어 비교한 뒤 보냄. 항상 스냅샷부터 읽어야 하는지 확인 필요 | `src/features/editor/session.ts` |
| 편집 묶음을 닫는 주체 | 클라이언트가 2초 무입력, 30초 경과, 편집 종료 때 종료 요청을 보냄. 서버도 같은 기준으로 닫으므로 시각 차이로 `EDIT_GROUP_CLOSED`를 받으면 새 묶음으로 다시 보냄. 클라이언트가 종료 요청을 보내야 하는지 확인 필요 | `src/features/editor/session.ts` |
| 이미 닫힌 묶음에 종료만 요청했을 때 | 모킹은 `EDIT_GROUP_CLOSED`로 응답하고 프론트엔드는 이미 닫힌 것으로 보고 넘어감 | `src/mocks/server.ts` |
| 편집 세션을 식별하는 방법 | 계약은 같은 편집 세션이 다른 요소를 저장하면 서버가 이전 묶음을 닫는다고 제안하지만 식별 방법은 인증 기능 때 정한다. 지금은 선택이 옮겨 가면 클라이언트가 종료 요청을 보냄 | `src/features/editor/session.ts` |
| 버전 충돌 때 서버 최신 내용을 얻는 방법 | 충돌 응답에는 현재 버전만 있어 이벤트로 받은 내용이나 스냅샷 재조회로 얻음 | `src/features/editor/session.ts` |
| 슬라이드에서 쓰는 글꼴의 웹폰트 제공 | 예제는 Pretendard를 쓰지만 웹폰트 파일이 없어 화면은 시스템 글꼴로 표시됨 | `src/shared/styles/tokens.css` |

## 모킹과 실제 연동의 구분

2026-11-18 기준 백엔드에는 계약 형식, 요소 수정 처리의 일부, 요청 식별자와 공통 오류 응답이 있지만 프론트엔드가 호출할 수 있는 `/v1` 기능 경로는 아직 열려 있지 않다. 그래서 실제 서버 연동은 한 건도 확인하지 못했다.

없는 경로에 대한 공통 오류 응답과 요청 식별자 헤더는 실제 서버로 확인할 수 있는 항목이다. 2026-11-18에 백엔드 `main` 사본을 따로 받아 실행해 보려 했으나 로컬 DB 접속 정보가 없어 서버가 뜨지 않아 확인하지 못했다. 서버 실행 환경이 준비되면 개발 프록시를 거쳐 이 두 가지부터 확인한다.

모킹 서버는 계약의 저장, 멱등, 이력 묶음, 이벤트 규칙을 메모리에서 흉내 낸다. 모킹으로 통과한 시험은 프론트엔드 코드가 계약과 일치한다는 뜻이다. 실제 서버의 동작을 보증하지 않는다.
